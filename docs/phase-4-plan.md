# فاز ۴ — تحلیل پیشرفته (برنامه اجرایی)

> وضعیت: 🚧 **پلن نهایی شد — آماده اجرا** (شاخه `arena/01a00fe9-arena-project`)
> سند بالادستی: [برنامه محصول](product-plan.md) · فاز قبلی: [فاز ۳ ✅](phase-3-plan.md) · [ران‌بوک رفرش](refresh-runbook.md)

## هدف فاز

فاز ۱ «عکس لحظه‌ای» داد، فاز ۲ میزبان را عملیاتی کرد (هزینه/رزرو/سود واقعی)، و فاز ۳ به بازار **حافظه و زمان** داد (مجموعه رقبا، تاریخچه قیمت، روند عرضه/اشغال، هشدار روزانه).

فاز ۴ میزبان‌یار را از «داشبوردی که باید باز کنی» به **مشاوری که خودش خبر می‌دهد و قیمت پیشنهاد می‌دهد** تبدیل می‌کند: بفهمد کدام تعطیلات واقعاً تقاضا را تکان می‌دهد، برای هر شب قیمت مستدل بدهد، هر هفته گزارش بدهد، و وقتی چند اقامتگاه دارد همه را در یک جا ببیند — بدون اینکه اسکرپ جدید یا وعده پیش‌بینی قطعی بدهد.

قول مستقیم برنامه محصول برای این فاز:

> *Iranian holiday and seasonal-demand analysis · Weather correlation · Data-driven pricing recommendations · Weekly reports · Alerts such as “your next weekend is priced below the local market” · Multi-property and multi-user support*

## معماری داده

همان تفکیک فاز ۲/۳: `data/` فقط‌خواندنی (مال پایپ‌لاین)؛ `var/mizbanyar.db` مال میزبان. مهاجرت نسخه ۳:

```sql
-- P4-01: چند اقامتگاهی (پایه همه‌چیز)
residences           (id PRIMARY KEY, room_id UNIQUE, title, created_at)
-- همه جدول‌های میزبان یک ستون residence_id می‌گیرند (default = اقامتگاه اول)
-- expenses, reservations, blocks, recurrings, competitor_sets, competitor_notes, alert_log

-- P4-02: تعطیلات قمری و کش تقاضا
holiday_calendar     (date PRIMARY KEY, kind TEXT, name TEXT, is_public_holiday INTEGER)
                     -- kind: 'solar' | 'lunar' | 'weekend' | 'season_peak'
demand_factors       (date PRIMARY KEY, season TEXT, is_holiday INTEGER,
                      holiday_name TEXT, weekday INTEGER, is_weekend INTEGER)

-- P4-03: گزارش هفتگی
weekly_reports       (id PRIMARY KEY, residence_id, week_start TEXT, week_end TEXT,
                      payload JSON, created_at TEXT, UNIQUE(residence_id, week_start))

-- P4-04: تنظیمات اعلان (خارج از اپ — فعلا فقط log)
notification_prefs   (residence_id PRIMARY KEY, channel TEXT, target TEXT,
                      weekly_enabled INTEGER DEFAULT 1, alerts_enabled INTEGER DEFAULT 1,
                      updated_at TEXT)

-- P4-05: آب‌وهوا (اختیاری)
weather_daily        (date PRIMARY KEY, tmin REAL, tmax REAL, precip REAL, source TEXT)
```

* مهاجرت `residences` داده فعلی را به `id=1, room_id=3297585` منتقل می‌کند؛ همه ردیف‌های قدیمی `residence_id=1` می‌گیرند.
* `holiday_calendar` در اولین اجرا از یک فایل ثابت `data/holiday-calendar-1403-1407.json` پر می‌شود (نه API خارجی در runtime).
* `weather_daily` فقط اگر کلید API در `.env` باشد پر می‌شود؛ نبودش هیچ صفحه‌ای را نمی‌شکند.

## مایلستون‌ها

### P1 — تقویم تقاضای ایرانی (تعطیلات + فصل) ✦ قلب تحلیلی فاز ۴

قول محصول: *Iranian holiday and seasonal-demand analysis*

**کار:**
- تکمیل `holiday_calendar`: اضافه کردن تعطیلات قمری متغیر ۱۴۰۳–۱۴۰۷ (عید فطر، قربان، غدیر، عاشورا، اربعین، رحلت پیامبر، شهادت امام رضا و ...) از منبع تقویم رسمی + برچسب‌گذاری در `dates.ts`
- تابع جدید `lib/demand.ts`:
  - `buildHolidayIndex()` — برای هر روز: آیا تعطیل رسمی است؟ فاصله تا نزدیک‌ترین تعطیلی چند روزه (پل تعطیلات)؟
  - `analyzeSeasonality(radarRooms, archivePrices, snapshots)` — اثر هر عامل روی `marketOccupancy` و `medianPrice` بازار: آخرهفته چقدر، تعطیل رسمی چقدر، پیک تابستان/نوروز چقدر
  - خروجی: جدول ضرایب توصیفی (مثلاً «جمعه +۱۸٪ اشغال، تعطیل رسمی +۲۷٪، مرداد +۳۴٪ نسبت به آذر»)
- UI:
  - کارت «تقویم تقاضا» در `/market`: هیت‌مپ ۱۲ ماهه (جلالی) با رنگ تقاضا + تولتیپ «چرا این ماه شلوغ است»
  - صفحه جدید `/insights` بخش «تعطیلات پیش رو» — ۶۰ روز آینده با برچسب تقاضا
  - نمودار فصلی: اشغال بازار به تفکیک `عادی / آخرهفته / تعطیل / پیک فصل`
- صداقت: اگر داده یک ماه کم باشد (مثلاً فقط ۱ برش آرشیو)، به‌جای عدد قطعی می‌نویسد «داده کافی نیست — بعد از `npm run archive` دقیق‌تر می‌شود»

**خروجی پذیرش:**
- `holidayName("1404-03-14")` همچنان «رحلت امام خمینی» و `holidayName("1404-12-10")` (عید فطر ۱۴۰۴) هم درست برمی‌گردد
- با دیتاست واقعی، ضریب آخرهفته > ۰ و ضریب تعطیل > آخرهفته محاسبه شود (تست fixture)
- هیت‌مپ با داده فعلی رندر شود و خطای فایل تقویم، صفحه را نشکند

### P2 — قیمت پیشنهادی داده‌محور و توضیح‌پذیر

قول محصول: *Data-driven pricing recommendations* (نه «تضمین فروش»)

**کار:**
- ارتقای `lib/jajiga/pricing.ts`:
  - ورودی جدید: `demandFactors` از P1 + `peerIndex` انتخابی (یا مجموعه ذخیره‌شده فاز ۳)
  - فرمول جدید (توضیح‌پذیر، بدون جعبه سیاه):
    ```
    base   = میانه رقبا برای همان شب (فقط شب‌های باز)
    season = ضریب فصل/تعطیلات از P1 (مثلاً +12% برای پل ۳روزه)
    quality= پرمیوم امتیاز (موجود)
    scarcity= کمیابی بازار آن شب (موجود)
    center = base × season × quality × scarcity  → رُند به ۵۰ هزار
    band   = [center×0.93 , center×1.09]  (مثل قبل، ولی کف/سقف هم توضیح دارد)
    ```
  - هر `SuggestedNight` یک `reasons: string[]` می‌گیرد: «تعطیلی رسمی»، «آخرهفته»، «پیک مرداد»، «امتیاز ۴.۹»، «اشغال بازار ۴۲٪»
- UI:
  - در `/calendar` هر شبِ باز: باند جدید + چیپ‌های دلیل (۳–۴ تایی، فارسی کوتاه)
  - در `/competitors/[id]` مقایسه «قیمت شما vs باند پیشنهادی آن شب»
  - Empty-state جدید برای شب‌های کم‌نمونه: به‌جای null خشک، «برای این شب هنوز نمونه کافی نداریم — میانه ماه مشابه: X تومان» (میانه همان weekday در همان فصل)
- تست: شب عادی vs شب تعطیل با price index یکسان، center تعطیل بالاتر باشد

**خروجی پذیرش:**
- با fixture دو حالته (شبیه‌سازی نوروز)، `suggestNightPrice` برای ۱ فروردین center بالاتری از ۱۵ آذر بدهد
- همه دلایل به فارسی و قابل تست (pure function) باشند
- شب‌های <۳ نمونه دیگر nullِ بی‌توضیح ندهند

### P3 — گزارش هفتگی + اعلان خارج از اپ (پلکان هشدار فاز ۳)

قول محصول: *Weekly reports · Alerts such as “your next weekend is priced below the local market”*

**کار:**
- `lib/reports.ts` (pure):
  - `buildWeeklyReport(residenceId, weekStart)` — KPI هفته (اشغال، ADR، RevPAN، سود واقعی از `finance.ts`)، مقایسه با هفته قبل، ۳ هشدار برتر از `alerts.ts`، تغییر عرضه منطقه، و ۳ توصیه قیمتی از P2
  - خروجی JSON + رندر HTML قابل چاپ (بدون PDF سنگین در فاز اول — `window.print()` کافی است)
- `lib/notify.ts` (آبسترکت):
  - `interface Notifier { sendWeekly(report): Promise<void> }`
  - پیاده‌سازی `LogNotifier` (فقط console/file) و `TelegramNotifier` (اگر `TELEGRAM_BOT_TOKEN` و `chat_id` در prefs باشد)
  - هیچ کلید یا توکنی در Git نمی‌ماند — فقط `.env.example`
- UI/API:
  - صفحه جدید `/reports`: لیست گزارش‌های هفتگی + دکمه «ساخت گزارش این هفته» + پیش‌نمایش چاپی
  - `GET /api/reports/weekly?residence=1` و `POST /api/notify/test`
  - تنظیمات در `/data` یا `/finance` بخش «اعلان‌ها»: انتخاب کانال، تست ارسال
  - اسکریپت `npm run report:weekly` برای cron دستی
- اتصال به تقویم: هشدار «آخرهفته پیش رو زیر کف باند است» از P2 حالا هم در `/` و هم در گزارش هفتگی می‌آید

**خروجی پذیرش:**
- با DB خالی، `buildWeeklyReport` برای هفته‌ای بدون رزرو هم گزارش خالیِ خوش‌فرم بدهد (نه خطا)
- `LogNotifier` در تست بدون شبکه کار کند؛ `TelegramNotifier` بدون توکن skip شود
- گزارش چاپی شامل تاریخ شمسی، اعداد فارسی و لوگوی میزبان‌یار باشد

### P4 — چند اقامتگاهی (پایه مقیاس‌پذیری)

قول محصول: *Multi-property support* (چند کاربر/احراز هویت به بعد موکول)

**کار:**
- مهاجرت `residences` + افزودن `residence_id` به همه جدول‌های میزبان (با default 1 و FK)
- `lib/db/repo.ts` — همه repoها `residenceId` پارامتر می‌گیرند؛ تابع `getActiveResidenceId()` از کوکی/query
- UI:
  - سوییچر اقامتگاه در `AppShell` (هدر) — لیست residences + «+ افزودن اقامتگاه»
  - فرم افزودن: `room_id` جاجیگا + عنوان + اتصال به `data/radar/[id].json` اگر موجود باشد، وگرنه حالت «بدون رادار» با بنر توضیح
  - همه صفحات (`/`, `/calendar`, `/finance`, `/competitors`, `/reports`) با `residenceId` فیلتر شوند
  - صفحه `/data` برای هر اقامتگاه جداگانه تازگی داده را نشان دهد
- بکاپ: `npm run db:export` حالا `{ residences, ... }` را هم شامل شود؛ `db:import` مهاجرت‌پذیر باشد

**خروجی پذیرش:**
- افزودن اقامتگاه دوم (مثلاً ۳۱۹۸۲۳۴) و ثبت یک هزینه برای آن، KPI اقامتگاه اول را تغییر ندهد
- سوییچ بدون رفرش سنگین کار کند؛ URL شامل `?r=2` شود تا اشتراک‌گذاری ممکن باشد
- تست: دو residence در DB حافظه‌ای، repoها تفکیک را رعایت کنند

### P5 — همبستگی آب‌وهوا (اختیاری، اگر وقت بود)

قول محصول: *Weather correlation*

**کار:**
- اسکریپت `scripts/fetch-weather.ts` — اگر `WEATHER_API_KEY` باشد، دمای روزانه بابل (۳ ماه اخیر) را می‌گیرد و در `weather_daily` می‌ریزد؛ وگرنه no-op
- `lib/weather.ts` (pure): همبستگی ساده پیرسون بین `tmax`/`precip` و `marketOccupancy` آخرهفته‌های همان هفته (بدون ادعای علیت)
- UI: کارت کوچک در `/market` تب «آب‌وهوا» — نمودار پراکندگی دما vs اشغال + جمله احتیاط‌آمیز «همبستگی لزوماً علیت نیست»
- اگر جدول خالی باشد، کارت می‌نویسد «داده آب‌وهوا ندارید — با `npm run weather:fetch` فعال کنید»

**خروجی پذیرش:**
- بدون API key هیچ صفحه‌ای نشکند
- با fixture مصنوعی (هفته‌های گرم‌تر = اشغال بالاتر)، ضریب همبستگی مثبت محاسبه شود

## ترتیب و وابستگی

```
P1 (تقویم تقاضا) ──► P2 (قیمت داده‌محور) ──► P3 (گزارش هفتگی)
        ▲                                        ▲
        │                                        │
P4 (چند اقامتگاهی) ──────────────────────────────┘  (مستقل ولی P3 را بهتر می‌کند)
P5 (آب‌وهوا) مستقل — آخر، اختیاری
```

**پیشنهاد اجرا:** `P1` (۲–۳ روز، ارزش تحلیلی فوری و بدون نیاز به آرشیو جدید) → `P4` (زیرساخت، موازی‌پذیر) → `P2` (روی P1 سوار است) → `P3` (روی P2+P1) → `P5` در فرصت.

هر مایلستون یک PR جدا با تست‌های `node:test` و DB حافظه‌ای — مثل فاز ۲/۳.

## تصمیم‌های فنی

- **ادامه الگوهای تثبیت‌شده:** مهاجرت نسخه‌دار در `lib/db/index.ts`، repo تایپ‌شده، zod مشترک، Route Handler + `revalidatePath`، تست pure بدون IO
- **توابع خالص برای تحلیل:** `demand.ts`, `pricing.ts`, `reports.ts`, `weather.ts` ورودی‌شان آرایه/مپ است، خروجی‌شان JSON — مثل `finance.ts` تست می‌شوند
- **بدون ML سنگین:** ضرایب فصلی با میانگین‌گیری مقطعی و میانه به‌دست می‌آید؛ اگر در آینده داده بیشتر شد، همین ضرایب می‌تواند ورودی یک رگرسیون ساده شود
- **تقویم قمری ثابت:** به‌جای محاسبه نجومی در runtime، یک JSON ثابت ۱۴۰۳–۱۴۰۷ در `data/` نگه می‌داریم (قابل بازبینی انسانی، بدون وابستگی خارجی)
- **اعلان آبسترکت:** `notify.ts` فقط interface است؛ پیاده‌سازی واقعی تلگرام/ایمیل بعداً بدون تغییر بقیه کد اضافه می‌شود
- **چند اقامتگاهی بدون auth:** فعلاً تک‌کاربره محلی — auth و PostgreSQL طبق برنامه محصول به استقرار عمومی موکول است
- **بدون اسکرپ جدید:** همچنان قانون `DATA-GUIDE.md` — «خودت اسکرپ نکن، از پایپ‌لاین Hermes بخواه»

## سنجه موفقیت فاز

پایان فاز ۴ یعنی میزبان بتواند **بدون ترمینال**:

1. ببیند کدام تعطیلات/فصل واقعاً بازار بابلکنار را تکان می‌دهد و هیت‌مپ تقاضا را بخواند ✅
2. برای هر شبِ تقویم، یک باند قیمت مستدل با ۲–۳ دلیل فارسی بگیرد ✅
3. هر هفته گزارش یک‌صفحه‌ای چاپی بگیرد و (در صورت تمایل) همان را در تلگرام دریافت کند ✅
4. اقامتگاه دوم را اضافه کند و KPI/تقویم/مالی را جدا ببیند ✅
5. (اختیاری) ببیند آیا هفته‌های گرم‌تر واقعاً شلوغ‌تر است یا نه — با توضیح «همبستگی ≠ علیت» ✅

## ریسک‌ها و mitigation

| ریسک | اثر | چاره |
|---|---|---|
| تعطیلات قمری هر سال جابه‌جا می‌شود | تقویم کهنه شود | JSON تا ۱۴۰۷ از الان + تست سالانه + یادآوری در `refresh-runbook.md` |
