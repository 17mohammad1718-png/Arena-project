# فاز ۲ — داده واقعی میزبان (برنامه اجرایی)

> وضعیت: 📋 برنامه‌ریزی‌شده · پیش‌نیازها کامل است
> سند بالادستی: [برنامه محصول](product-plan.md) · [راهنمای داده](DATA-GUIDE.md)

## هدف فاز

فاز ۱ یک داشبورد **فقط‌خواندنی** ساخت که همه‌چیز را از فایل‌های `data/` می‌خواند.
فاز ۲ میزبان‌یار را به **ابزار عملیاتی روزمره میزبان** تبدیل می‌کند: میزبان بتواند
داده خودش (هزینه‌ها، رزروها، بلاک‌ها) را داخل خود اپ ثبت کند، این داده‌ها **پایدار**
بمانند، و در نتیجه برای اولین بار **سود واقعی** (نه فقط درآمد منهای کمیسیون)
قابل محاسبه شود.

## چرا این‌ها؟ (شکاف‌های واقعی داده امروز)

بررسی دیتاست فعلی این شکاف‌ها را نشان می‌دهد:

| شکاف | اثر فعلی |
|---|---|
| هیچ‌جا هزینه ثبت نمی‌شود (نظافت، ملحفه، شارژ، تعمیر، …) | «درآمد خالص» فعلی فقط `ناخالص − کمیسیون ۱۲٪` است؛ سود واقعی نامعلوم است |
| درآمد محقق‌شده فقط یک برش ۶ شبه دارد (`realized-seydkola`، ۷ تا ۱۲ آگوست) | روند ماهانه/فصلی درآمد قابل ساختن نیست؛ هر رفرش، برش قبلی را از دست می‌دهیم |
| بلاک‌های دستی با اسکریپت بیرونی (`manual_block.py`) در `manual-blocks.json` ثبت می‌شوند | میزبان برای یک کار روزمره باید ترمینال باز کند؛ خطاپذیر است |
| رزرو از `is_unavailable` رادار **استنباط** می‌شود | مبلغ واقعی پرداختی مهمان، تعداد مهمان و تخفیف توافقی جایی ثبت نیست |
| تقویم رادار فقط ~۹۸ شب آینده را می‌بیند | گذشته‌ای انباشته نمی‌شود؛ مقایسه «این ماه با ماه قبل» ممکن نیست |

## معماری داده فاز ۲

```
data/          ← منبع فقط‌خواندنی بازار (خروجی پایپ‌لاین Hermes) — دست نمی‌خورد
var/mizbanyar.db  ← SQLite محلی (better-sqlite3) — داده خود میزبان، خارج از Git
```

- **اصل تفکیک:** داده بازار (متعلق به پایپ‌لاین) از داده میزبان (متعلق به اپ) جدا می‌ماند.
  `getDataset()` همچنان `data/` را می‌خواند؛ یک لایه جدید `getHostData()` دیتابیس را.
- `var/` به `.gitignore` اضافه می‌شود + اسکریپت `npm run db:export` که کل دیتابیس را
  به JSON قابل‌بکاپ خروجی می‌دهد (و `db:import` برعکس).
- همه تاریخ‌ها در دیتابیس **میلادی ISO** ذخیره می‌شوند (مطابق قرارداد `data/`)؛
  ورود و نمایش همیشه **شمسی** است (از `dates.ts` موجود).
- مبالغ به **تومان** و صحیح (integer) ذخیره می‌شوند.

### جدول‌های SQLite

```sql
expenses      (id, date, amount, category, note, recurring_id NULL, created_at)
recurrings    (id, title, amount, category, day_of_month, active)   -- هزینه ماهانه ثابت
reservations  (id, check_in, check_out, guests, gross_amount,
               discount_amount, source TEXT DEFAULT 'manual',        -- manual | radar | import
               status TEXT DEFAULT 'confirmed',                      -- confirmed | cancelled
               note, created_at)
blocks        (id, date UNIQUE, reason, created_at)                  -- جایگزین manual-blocks.json
archive_realized (id, captured_at, range_start, range_end, room_id, payload JSON)
archive_prices   (id, captured_at, date, room_id, price, is_unavailable)
```

## مایلستون‌ها

### M1 — زیرساخت ذخیره‌سازی ✦ پایه همه‌چیز

- افزودن `better-sqlite3` + ماژول `src/lib/db/` (اتصال، مهاجرت‌ها، تایپ‌های TS)
- Route Handler های Next برای CRUD (`/api/expenses`, `/api/reservations`, `/api/blocks`)
- مهاجرت یک‌باره: ایمپورت `manual-blocks.json` به جدول `blocks` در اولین اجرا
- `npm run db:export` / `db:import`
- **خروجی پذیرش:** دیتابیس ساخته می‌شود، بلاک موجود (۱۴۰۵/۰۵/۲۵) داخل اپ دیده می‌شود، تست‌های CRUD سبز

### M2 — ثبت هزینه و سود واقعی ✦ بیشترین ارزش برای میزبان

- صفحه جدید «مالی من» (`/finance`): فرم ثبت هزینه با تاریخ شمسی، دسته
  (نظافت، ملحفه، شارژ و قبوض، تعمیرات، خرید وسایل، ایاب‌ذهاب، متفرقه)، مبلغ، یادداشت
- هزینه‌های تکرارشونده ماهانه (مثل حقوق سرایدار) با یک‌بار تعریف
- شاخص جدید در نمای کلی: **سود خالص واقعی = درآمد − کمیسیون − هزینه‌ها**
  و «سود هر شبِ فروخته‌شده»
- نمودار هزینه به تفکیک دسته + نسبت هزینه به درآمد
- **خروجی پذیرش:** میزبان هزینه ثبت می‌کند و بلافاصله سود خالص در `/` و `/finance` تغییر می‌کند

### M3 — ثبت و تصحیح رزرو در اپ

- ثبت رزرو دستی: بازه اقامت (ورود شمسی)، تعداد مهمان، مبلغ واقعی، تخفیف، یادداشت
- تقویم `/calendar` تعاملی می‌شود: کلیک روی شب → «بستن شب» (بلاک) یا «ثبت رزرو»
- قانون ادغام: رزرو ثبت‌شده دستی بر استنباط رادار **مقدم** است؛
  شب‌هایی که رادار «رزرو» می‌بیند ولی رزرو دستی ندارند با برچسب «استنباطی» می‌مانند
- ثبت کنسلی (وضعیت `cancelled`) و اثرش بر نرخ اشغال طبق تعریف‌های README
- **خروجی پذیرش:** KPI های اشغال/ADR/RevPAN از ترکیب داده دستی + رادار درست درمی‌آیند (تست e2e)

### M4 — ایمپورت CSV/Excel

- پیاده‌سازی قرارداد ایمپورتی که در برنامه محصول تعریف شده
  (`reservations.csv`, `expenses.csv`, `blocked.csv`) — این‌بار از طریق UI آپلود
- نگاشت ستون‌ها با پیش‌نمایش، نرمال‌سازی تاریخ شمسی/میلادی، ارقام فارسی،
  جداکننده هزارگان و «تومان» (منطق موجود در برنامه محصول §Data ingestion)
- ردیف‌های نامعتبر رد نمی‌شوند که گم شوند — با دلیل در همان صفحه نمایش داده می‌شوند
- **خروجی پذیرش:** یک فایل اکسل واقعی میزبان بدون دستکاری ایمپورت می‌شود

### M5 — آرشیو تاریخچه (پل به فاز ۳)

- فرمان `npm run archive`: برش فعلی `realized-*.json` و قیمت‌های رادار را
  با مهر زمان در جدول‌های آرشیو ذخیره می‌کند (idempotent — اجرای تکراری، رکورد تکراری نمی‌سازد)
- بعد از هر رفرش دیتاست توسط پایپ‌لاین، یک اجرا کافی است
- نمودار روند درآمد ماهانه در `/revenue` وقتی ≥ ۲ برش آرشیو موجود باشد
- **خروجی پذیرش:** دو بار آرشیو با داده متفاوت → نمودار روند ظاهر می‌شود
- *این همان داده‌ای است که فاز ۳ (تاریخچه قیمت رقبا و بنچمارک زمانی) لازم دارد.*

## ترتیب و وابستگی

```
M1 ──► M2 ──► M3 ──► M4
 └────────────────────► M5 (مستقل از M2-M4، فقط به M1 نیاز دارد)
```

پیشنهاد اجرا: **M1 + M2 با هم** (یک قابلیت کامل و ملموس: سود واقعی)،
بعد M5 (ارزان و حیاتی برای انباشت تاریخچه — هر روز تأخیر یعنی داده از دست رفته)،
بعد M3، و M4 در انتها.

## تصمیم‌های فنی

- **better-sqlite3** (سنکرون، بدون سرور، مناسب Route Handler ها) — مطابق پیشنهاد
  «SQLite برای پروتوتایپ محلی» در برنامه محصول
- فرم‌ها client component + اعتبارسنجی **zod** مشترک بین کلاینت و API
- کامپوننت ورود تاریخ شمسی روی `date-fns-jalali` موجود ساخته می‌شود (وابستگی جدید UI نمی‌خواهد)
- `revalidatePath` بعد از هر نوشتن، تا صفحات سروری بلافاصله تازه شوند
- تست‌ها با همان `node:test` موجود + دیتابیس موقت در حافظه
